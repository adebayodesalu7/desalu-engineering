REQUIRED FOR ALL RELEASES

Before every upload

  1. Confirm distribution rights. You must own the work or have permission to redistribute it, including its images, fonts, libraries, and other bundled assets. State the actual license; do not guess.
  2. Remove private material. Exclude passwords, API keys, signing files, environment files, private certificates, customer data, personal data, and client-only content. Never upload an Android signing keystore or its passwords.
  3. Prepare the listing information. Provide a clear title, unique lowercase resource ID, author/publisher, short description, license, version, platform/runtime requirements, installation steps, and release notes.
  4. Use the right version. Reuse the resource ID for updates and provide a new version for each release. Do not replace or reuse an already published version.
  5. Test the exact package. Install or run the selected archive on a clean, compatible environment and verify the setup instructions match the package.
  6. Use public HTTPS media links carefully. Icon and screenshot URLs are shown to library visitors; the image host may receive visitor connection data. Use a trusted host and only images approved for public display.
  7. Respect the file limit. Each uploaded file must be no larger than 50 MiB. Android builds and their source ZIP are separate files and each has its own limit.
  8. Review the preview. Check the public-facing title, description, version, requirements, and selected files before confirming the review attestation and publishing.
A

ANDROID

Publish an Android app

  1. Build a release APK for direct installation, or an AAB for Google Play distribution. An AAB is not a normal tap-to-install package.
  2. For direct-download users, prefer a properly release-signed APK for the device architecture you support. Test installation and opening it on a compatible device or emulator.
  3. Do not publish a debug-signed production build. Keep your release keystore and passwords private and backed up; never include them in the source ZIP.
  4. Prepare a clean source project ZIP with the app source, build files, lockfiles, and README. Exclude generated build/cache folders, local properties, signing files, `.env` files, keys, and private data.
  5. In the Android publishing form, select APK or AAB to match the actual file, upload the build and source ZIP separately, and provide platform requirements, setup steps, license, and a release changelog.

The current upload limit is 50 MiB per file. If the APK is too large, investigate architecture-specific release splits and unused native libraries; do not remove required app features blindly.

WORDPRESS

Publish a WordPress theme

  1. Package one installable theme in a ZIP with the theme folder at the archive root. Include the required `style.css` theme header and the theme's PHP, templates, scripts, styles, and owned assets.
  2. Keep application behavior that should survive a theme change—custom post types, shortcodes, and business logic—in a companion plugin rather than the theme.
  3. Verify the stated license and all bundled assets. Remove production credentials, customer content, and unnecessary demo data.
  4. Install the exact ZIP on a clean WordPress site. Test activation, key templates, menus, responsive layouts, and supported WordPress/PHP versions.
  5. Choose “WordPress theme” in the form and provide the supported WordPress version, PHP requirement, other dependencies, installation steps, and release notes.

P

WORDPRESS

Publish a WordPress plugin

  1. Package one installable plugin in a ZIP with its plugin folder at the archive root and a main PHP file containing a valid WordPress plugin header.
  2. Document what the plugin does, required plugins/services, permissions, and any data it stores or sends. Include an uninstall/data-retention note when relevant.
  3. Check license compatibility and bundled assets. Search for credentials, private endpoints, debug data, and customer information; remove them before packaging.
  4. Install and test the exact ZIP on a clean WordPress site with the supported PHP/WordPress versions. Test activation, core features, deactivation, and uninstall behavior.
  5. Choose “WordPress plugin” in the publishing form and provide the exact tested compatibility, dependencies, setup instructions, license, and changelog.

iOS

APPLE PLATFORMS

Publish an iOS app project

  1. Prepare a clean Xcode source ZIP containing the `.xcodeproj` or `.xcworkspace`, source files, required project assets, and setup documentation.
  2. Exclude signing certificates, provisioning profiles, private keys, local environment files, credentials, personal data, and generated build folders.
  3. Document the minimum iOS version, Xcode/toolchain, required services, permissions, and any configuration a developer must supply locally.
  4. Unzip and build the project in a clean compatible Xcode environment. Test the app on a supported simulator or device and confirm the setup notes are accurate.
  5. Upload the source ZIP and provide its version, license, requirements, setup steps, and release notes. This workflow publishes source code, not an App Store-signed binary.

WEB

Publish an HTML / CSS / JS project

  1. Package the working website or web project in a ZIP with a clear root folder and a README that explains prerequisites and how to run it.
  2. Include the necessary source and assets; exclude dependency caches, generated artifacts that can be rebuilt, secrets, `.env` files, credentials, and private data.
  3. Replace development-only URLs and local paths where needed. Document runtime versions, external services, environment variables by name only, and any required setup.
  4. Test the exact ZIP from a clean extraction. Check navigation, mobile layout, console/network errors, and any required API or backend configuration.
  5. Choose “HTML / CSS / JS” in the publishing form and provide the correct license, requirements, setup instructions, and changelog.
